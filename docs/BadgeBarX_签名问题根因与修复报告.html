BadgeBar X 1.3.7 · 「不生效 / 设置面板报错」根因定位与修复

设备：iPhone 15 Pro Max（A17 Pro / arm64e）· iOS 17.2.1 · Relaxin（RootHide 隐根）
根因：代码签名格式过旧 产出：v5（双 CodeDirectory） 4 切片 × 2 算法全部校验通过

一、结论先说

你截图里那句 code signature invalid 就是「不生效」的唯一原因。路径、目录布局、依赖全都正常——文件被找到了、dyld 也读到了它，只是 签名校验没通过，内核直接拒绝加载。

而设置面板与插件本体硬链接同一批依赖、共用同一套签名，所以同一个病因同时造成了两个现象：

  • 设置面板 → 弹错误框（你看到的截图）
  • 插件本体 BadgeBar.dylib → 静默不生效（SpringBoard 里没加载成功，不会有任何提示）

我上两轮把原因归到「缺依赖库」，那个方向是错的。真正的问题是签名格式——本轮已用你提供的 Donut 参照包逐字节比对确认。

三、根因：签名是 2019 年的老格式，iOS 17 不认

我把 roothide 官方源上的 12 个真实隐根插件包（含你给的 Donut 2.0.3）全部解包，逐字节读它们的 CodeDirectory，结果12/12 完全一致，而原包 / 我之前的产物是一个异类：

签名属性12 个官方隐根包（可正常工作）原包 / 我的 v1–v4
CodeDirectory 版本0x20400（全部）0x20001（2019 年 ldid 老格式）
是否含 SHA-256 的 CD12/12 都有一个都没有
哈希算法SHA-256（+ 部分含 SHA-1 双份）仅 SHA-1
execSeg 字段有（execSegLimit = __TEXT.vmSize）老版本头里根本没有这些字段
页哈希自校验全部 0 失败自洽（但不是 iOS 17 认的格式）

Donut 的签名布局（逐字节读出来的，作为标准答案）

SuperBlob (count=3)
├─ idx[0] type=0x0000  CodeDirectory   SHA-1    hashSize=20  version=0x20400
├─ idx[1] type=0x0002  Requirements     内部需求
└─ idx[2] type=0x1000  CodeDirectory   SHA-256  hashSize=32  version=0x20400
                       ↑ 两个 CD 都带 execSegBase/Limit/Flags

两个 CD 覆盖同一段代码、用两种算法各存一份页哈希；内核取「最高等级」的那个（SHA-256）做校验。我的旧产物只有 SHA-1 那一份，且版本号停在 0x20001 —— 这就是 AMFI 判它 invalid 的原因。

四、这次改了什么

只动代码签名区域，业务代码一个字节没改：

#改动对象
1重建 SuperBlob = SHA-1 CD + Requirements + SHA-256 CD，两个 CD 均为 version 0x20400BadgeBar.dylib（arm64 / arm64e）
2同上BadgeBarPrefs（arm64 / arm64e）
3补上 execSegBase=0 / execSegLimit=__TEXT.vmSize / execSegFlags=0两个二进制的两个切片
4原 Requirements 内部需求原样保留，两种算法各自算一遍它的哈希写进 slot -2全部
5按需扩展 LC_CODE_SIGNATURE.datasize 与 __LINKEDIT filesize/vmsize，并同步 fat 头里的切片 size 字段全部（签名区变大，需向文件尾追加）
6tar 内属主规范为 root:wheel（原包是 33:33 = _www）全部 16 个成员
7control 版本号 → 1.3.7-roothide5，追加修复说明control

代码段/数据段/字符串/动态库链接全部与 v4 逐字节一致；签名区之前的差异字节只有 4–5 个，全部是上面第 5 条的尺寸字段（已逐个核对：0x810/0x811=datasize、0xcdc/0xcdd=LINKEDIT filesize 等）。

七、老实说：这轮我修正了前两轮的判断

  • 上一轮我把原因归为「缺依赖库」，依据是「设置面板与插件本体的报错同源」。方向对（确实同源），但归因错了——同源的是签名，不是依赖。
  • 我此前的签名校验器是「自洽但不够」：它只按包内已有的 SHA-1 CD 去算页哈希，算出 18/18、13/13 就报「签名有效」。它无法发现「这套格式 iOS 17 根本不接受」。这轮我重写了一个独立校验器，并引入官方包作为基准，才暴露出格式问题。
  • 顺带纠正一个更早的误判：原包的 SHA-1 签名其实是自洽的（我早期报「15/18 失效」是校验器算法写错）。真正的问题从来不是「哈希算错了」，而是「格式太老」。

八、仍未真机验证

以上全部是离线静态校验：签名结构、双 CD 页哈希、fat 头、段布局、control 都能从包里被证明。但「装上后内核接受这个签名」属于运行时行为，必须上设备实测。

判断依据很明确：设置面板能否打开是最灵敏的指标——它一旦能开，说明签名与依赖两关都过了，插件本体也必然加载成功。

附带说明：arm64e 的 cpusubtype 是 0x2 还是 0x80000002 都不是判据——官方包两种写法都有（iconTime 是 0x2，Donut 是 0x80000002），都能正常工作。

九、这一版修复现在可以「一键复现」

为避免以后再出现「手工修出来的包没法再生成一遍」，我把这轮的全部结论固化进了 C:\Users\张培斌\.workbuddy\skills\ios-deb-roothide-port\ 这套技能里， 现在从原始有根包一条命令就能复现出与 roothide5 等价的产物：

python scripts/roothide_convert.py "BadgeBar X-1.3.7.deb" OUT.deb \
    --version 1.3.7-roothide5 --extra-deps rootless-compat \
    --weak-link 'BadgeBarPrefs=@loader_path/.jbroot/usr/lib/libcolorpicker.dylib'
python scripts/audit.py OUT.deb "BadgeBar X-1.3.7.deb"
